# 性能观察与复现

性能结果按版本和测量方法区分。运行观察反映当时负载，不直接代表稳定容量或新文档的吞吐上限。

## 1.3.1 四卡运行观察

环境为四张 L40，MinerU 4.0.12、vLLM 0.29.0。每卡 8 个独立解析进程，总共 32 个，其中 2 个仅领取高优任务；各卡共享一个 vLLM 副本。

| 观察指标 | 结果 |
| --- | ---: |
| 观察时长 | 45.27 秒 |
| 成功完成任务 | 21 |
| 成功完成页数 | 2115 |
| 开始 / 结束时在途任务 | 19 / 11 |
| 结束时等待任务 | 0 |
| 四卡平均 GPU 利用率 | 26.5% / 17.5% / 24.1% / 19.0% |
| 各卡显存峰值 | 低于 29 GiB |
| 移除临时盘限制后的新增解析错误 | 0 |

旧线程模式的一段观察为 7.2% / 9.2% / 10.1% / 3.2% 平均 GPU 利用率。两段文档与到达流量不同，不能据此计算同文档的性能倍数。观察末尾没有排队，继续增加进程未必能提高当时的利用率。

试点中的错误源于固定 2 GiB 的 `/tmp` 被页面原始位图写满，不是 GPU 显存不足。现已使用容器磁盘和 Linux 页缓存。完整验证范围见[验证说明](development.md)。

## 复现方法

使用自己的文档分布，先预热，再测量固定到达速率与排空时间：

```bash
.venv/bin/python scripts/load_test.py http://127.0.0.1:3888 samples/*.pdf \
  --rate 0.2 --duration 60 --drain-seconds 600 --output artifacts/load-test.md
```

脚本关闭 API 内容缓存和在途去重，报告接收、拒绝、失败、未完成、提交窗口和包含排空的吞吐，以及 P95/P99。默认示例不带鉴权；启用业务密钥时需给压测客户端增加同样的 Bearer 请求头，不能将密钥写入报告或仓库。

比较进程数时保持文档、档位、输出选项、到达速率、模型和缓存策略一致。分别观察排队、SDK 阶段、失败率、显存峰值与 vLLM 内部排队；SDK 计时有嵌套，不能简单相加。指标口径见[可观测性](observability.md)。

旧同步版本和 1.1 单卡/双卡的固定样本测量保留在[历史基准](archive/benchmark-1.1.md)，不作为当前容量结论。
